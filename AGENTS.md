# Working on mkapp

This file governs implementation and documentation changes throughout this repository. The project is currently a design, not an implemented framework.

## Project intent

Build a minimal Python desktop framework on ImGui-Bundle for ad hoc data-science and trading apps. Features are plugins using the public SDK. A trusted local feature can be added by placing it in the application's `plugins/` directory and restarting. Plugins can be headless, depend on other plugins and load from local directories or approved installed wheels.

Read `ARCHITECTURE.md` for contracts and `PLAN.md` for delivery order before changing behavior. Preserve the user's latest requirements when they refine the design. If a new requirement changes a contract, update the architecture, plan, examples and affected tests together.

## Non-negotiable boundaries

1. All ImGui, HelloImGui and graphics operations execute on the main GUI thread. Render callbacks are synchronous and short. Never wait for a bus reply, worker or disk/network operation in a render callback.
2. ZeroMQ sockets are created, used and closed by their owner thread. One shared context is allowed; sharing sockets across threads is not. Close socket owners before terminating the context.
3. Plugin business communication uses SDK actions serialized by MessagePack. Exceptions are documented direct sensitive operations, reusable render component invocation and host lifecycle hooks.
4. Raw secrets, sensitive documents and private handles never enter action messages, ordinary workers, global state, cache, local storage, config, history, layout, telemetry or logs.
5. Imported plugins are trusted arbitrary Python code. Never describe SDK grants, Python modules, worker processes or ZeroMQ as a security sandbox.
6. Secure storage fails closed. No plaintext/null fallback, homemade cryptography or plugin-switchable privacy downgrade.
7. No hot loading/unloading or source reloading. Desired enablement and actual lifecycle state remain distinct.
8. All queues, encoded frames, decoded structures, concurrency and shutdown waits are bounded.

## Scope and minimalism

- Prefer the smallest end-to-end implementation that satisfies the current milestone.
- Keep a one-module plugin with a descriptor a viable starting point. Use ordinary Python for work within the same plugin and execution domain. Add SDK registrations when a feature needs to expose behavior, own host resources or cross an execution boundary.
- Keep market data, dataset models, strategies and broker integrations in application plugins. Keep full datasets with their owners and pass bounded summaries, pages or samples through SDK actions.
- Keep one package, one SDK registration model and one action protocol initially.
- First-party optional features use the same SDK registrations as third-party plugins.
- Use standard-library facilities before adding dependencies. Explain and document a new runtime dependency.
- Keep DuckDB confined to the optional local storage provider. Do not add a second UI abstraction, generic IoC container, additional database, remote broker, marketplace or distributed subsystem speculatively.
- Keep optional features independently disableable according to the architecture's explicit dependencies.
- Guard optional contributions with SDK feature checks; declare mandatory host features in plugin metadata so disabled services fail before import.
- Do not turn a spike into an abstraction without a concrete caller and a stable contract.

## Public SDK and extension rules

- `mkapp.sdk` is the supported plugin boundary. Public types and lifecycle methods have annotations and short execution-domain documentation.
- All first-party and third-party plugins inherit `mkapp.sdk.Plugin`. Entry-point factories return `Plugin` instances; reject invalid results before preparation.
- All executable request actions inherit `Action`, including subclasses generated by `@action(id)`. All plugin windows inherit `Window`. Register classes explicitly through `ctx.actions.register` and `ctx.windows.register`. Validate required overrides and metadata and reject conflicts before use. Do not maintain parallel callable-handler or WindowSpec/factory registration APIs.
- Keep `Plugin` limited to no-op `prepare(ctx)` and async `start(ctx)`/`stop(ctx)` lifecycle defaults. Override only needed hooks; no required superclass calls, abstract UI methods, hidden registration or subclass discovery.
- Supply bus, workers, windows, state, private operations and ownership through the host-created `PluginContext`. The base class does not create services or inject context implicitly. Host resource cleanup must not depend on calling a superclass hook.
- Use domain-specific host-created `WindowContext` and invocation-scoped `ActionContext` for windows/actions. Constructors take no arguments, perform no I/O/registration and create no hidden executors. Inheritance or a class reference never grants capabilities.
- SDK import must not initialize GUI, credentials, threads, processes or sockets.
- Expose the upstream `imgui_bundle` module lazily through `mkapp.sdk`. Keep GUI initialization and all rendering on the GUI thread.
- Plugins never import another plugin's internals or private host modules. Dependencies provide action contracts and SDK-resolved components.
- Registrations use stable namespaced IDs, explicit contract versions, ownership and idempotent disposal handles.
- The host's resource scope tracks every subscription, task, worker, registration and window. Partial startup failures must clean up that scope.
- Singleton providers are explicitly selected at bootstrap. Reject ambiguous providers and duplicate action/command/component IDs.
- Extensibility must not bypass immutable security rules. Provider overrides retain validation, lifecycle and privacy contracts.
- Document breaking changes and update SDK/manifest/wire/action versions as appropriate; do not silently change a published payload meaning.

## Discovery and lifecycle

- Discover and validate static metadata before importing plugin code.
- Discover immediate child directories with descriptors in the app-local `plugins/` folder, plus explicitly approved roots and installed distributions. Anchor the default folder to the app entry script or explicit app root. Reject paths that escape approved sources and avoid recursive scans.
- Default to all eligible discovered plugins when `enabled_plugins` is omitted or `None`. Treat an explicit list as an allowlist, including an empty list. Apply saved toggles within that selection and honor safe mode and source policy.
- Reject duplicate IDs, conflicting import packages, malformed/incompatible descriptors and hard dependency cycles deterministically.
- Never install/download packages or auto-enable plugins during startup dependency resolution.
- Distinguish Python distribution dependencies from plugin runtime dependencies.
- Start required dependencies first and stop dependents first. A failed required plugin blocks dependents, not unrelated plugins.
- Keep the private inventory regardless of optional public registry announcements.
- Announce readiness only after successful start; never claim that Python modules have been physically unloaded.

## Actions, state and concurrency

- An Action class declares its stable ID, input/output validators and bounded execution metadata, and implements `async handle(payload, ctx: ActionContext)`. The host creates one instance per registration on the runtime thread.
- Keep `@contract` equivalent to `@dataclass(frozen=True)`. For `@action(id)`, infer the frozen input and output dataclasses from the async function's annotations at registration. Validate and compile adapters once. Decode and validate the wire map before constructing the request and validate the response before encoding. Use the same host execution defaults, privacy rules and dispatch path as handwritten actions.
- Keep Action instances stateless by convention. Request data and caller/deadline/cancellation context stay local to handle; persistent state belongs to the owning service. Never retain invocation contexts, including when concurrency is one.
- Normalize local Action-class references, shared contract references and string IDs to the same bus route. Never invoke classes directly as a shortcut or serialize implementation objects. Cross-plugin consumers use IDs/contract-only packages rather than importing provider implementations. Events remain validated message contracts.
- Keep `@on(event)` metadata-only. Register decorated async handlers explicitly through `ctx.events.subscribe` and apply ordinary subscription validation, ownership and cleanup. Reserve `BaseEvents` publication for the host. Lifecycle event delivery is best effort, including forced shutdown. Required setup and cleanup use host lifecycle hooks and scopes.
- Validate both request and response contracts. Stamp source identity from the host connection, not caller-provided bytes.
- Use MessagePack's bounded primitive-value subset with string map keys, explicit protocol versions and enforced size/depth/item limits.
- Do not use pickle or ZeroMQ Python-object helpers for action messages.
- Do not execute handlers inline in the broker's routing loop. Use bounded per-owner tasks/executors.
- Cancellation/timeouts are best effort. A timeout does not prove a side effect did not occur; do not retry automatically.
- Preserve authoritative snapshots/revisions for registry and state recovery; events are not durable truth.
- State is non-sensitive and single-writer. Use compare-and-set for read/modify/write workflows that require conflict detection.
- Cache only recomputable non-sensitive values. Enforce owner namespaces, TTL, capacity and lifecycle cleanup. A miss must leave the application able to recompute.
- Keep DuckDB connection creation, use and closure on one storage thread. Use bounded queues, fixed parameterized statements and commit before acknowledging durability. Never expose raw SQL or native connections through the SDK.
- Worker kind is explicit: async, blocking I/O thread or CPU process. Do not advertise arbitrary inferred parallelization.
- Thread workers must cooperate with shutdown; spawned workers must not inherit GUI contexts or secret handles.
- Ignore stale GUI completions using owner scope generation and apply valid snapshots only at frame boundaries.

## UI and command rules

- A Window subclass declares ID/title and implements `render(ctx: WindowContext)`. The host constructs a separate instance per open request on the GUI thread; optional `on_open`/`on_close` hooks default to no-ops. Opening arguments come from `ctx.arguments`.
- Keep mutable UI state on each window instance. The host owns outer Begin/End, ID scoping, callback delivery and cleanup; window code balances its nested widget scopes. Window construction/hooks/render/completions all stay on the GUI thread.
- Closing revokes the WindowContext and discards outstanding callbacks. Host cleanup runs even when lifecycle hooks fail and never requires a superclass call.
- Encapsulate version-sensitive docking calls in the UI adapter. Plugins pass stable window IDs and placement intents, never native pointers/node IDs.
- Floating windows work when tile management is disabled.
- Reusable components scope ImGui IDs by caller and instance, document resource ownership and emit intents through the caller.
- Balance every ImGui Begin/End stack, including exception paths; prefer scoped SDK helpers.
- Palette commands dispatch registered actions through the same validation as any other caller.
- Parse the documented bounded grammar. Never use `eval`, `exec`, arbitrary imports or attribute execution on user command text.
- Autocomplete remains a separate extension; the palette must work without it.
- Private inputs use direct private prompts, not inline palette fields. Never persist raw command history by default.

## Privacy implementation rules

- Use synthetic data in tests, examples and screenshots. Never copy production credentials into fixtures.
- Safe diagnostics allowlist metadata and use sanitized error codes; do not log payloads, raw exception strings, paths or window titles indiscriminately.
- Keep telemetry and remote crash uploads off; adding them requires a deliberate architecture change and explicit user policy.
- Verify the actual credential backend and its platform behavior, including lock state and shared interpreter access.
- Keep private-operation input/results out of ordinary result bridges; return handles unless explicit safe declassification is part of the operation contract.
- Revoke grants/handles during owner cleanup and application lock. Reject stale lifecycle generations.
- Do not promise reliable secret zeroization in Python or native widgets.
- Disable uncontrolled ImGui INI persistence; persist only safe opaque layout metadata when enabled.
- Larger sensitive records require an approved encrypted backend; the keyring and global state are not substitutes.

## Coding and repository practice

- Use the repository's supported Python version, formatter, linter and type checker once established in M1. Do not invent successful commands or checks before tooling exists.
- Prefer OOP for entities with behavior and ownership: shallow `Plugin`, `Window` and `Action` base classes. Keep small protocols for service/provider contracts and dataclasses/simple records for configuration, specs, results and placement. Avoid deeper hierarchies, automatic subclass discovery and magic decorators.
- Use `pathlib`, explicit encodings, monotonic timeouts and typed structured errors. Write config/state atomically.
- Keep filesystem/network side effects out of module import.
- No dependency pin changes without checking the affected API and running relevant integration checks.
- Avoid changing unrelated code, regenerating unrelated files or overwriting existing user work.
- Never commit credentials, payload captures, sensitive dumps, development environments or downloaded transfer helpers.
- Do not leave implementation scaffolding pretending to satisfy a requirement. Label deliberate stubs and document unavailable behavior.

## Verification expectations

Run checks proportional to the change and the current milestone. Favor tests at public contracts and failure boundaries over tests that mirror private implementation details.

| Changed area | Required evidence |
| --- | --- |
| Plugin composition | Add and disable a consumer through configuration, with the provider and unrelated plugins unchanged |
| Metadata/dependencies | Default folder and default enablement, explicit and empty allowlists, disabled-import guard, path containment, cycle/version/duplicate fixtures and deterministic order |
| Lifecycle/resource scope | Inherited no-op hooks, invalid factory result, partial start failure, reverse stop, deadline and cleanup even when stop raises |
| Bus/codec | Real ZeroMQ round trip, invalid/oversized input, pressure, timeout and source validation |
| Event subscriptions | Decorator metadata and explicit activation, host-only base events, readiness, registry disabled, owner cleanup and bounded shutdown |
| Action objects | Required metadata/override validation, per-registration lifetime, isolated concurrent invocation contexts and class/reference/ID wire equivalence |
| Annotated actions | Frozen contract alias, registration-time signature/schema rejection, dataclass round trip, malformed requests and responses, handwritten/decorated wire equivalence |
| Workers/bridge | No GUI blocking, cancellation, late result, spawned process and owner shutdown |
| Sensitive service | Synthetic sentinel leakage checks, grant expiry/revocation, fail-closed backend |
| State | CAS conflict, delete/recreate revision, overflow recovery and persistence failure |
| Cache | TTL, null versus miss, entry/byte pressure, namespace authorization and cleanup |
| Local storage | Real DuckDB reopen, rollback, lock, migration/refusal, private-value rejection, disabled import and owner-thread shutdown |
| Palette/completion | Grammar, spans, typed fields, malformed input and stale async completion |
| UI/docking | GUI-thread construction/hooks/render/completions, isolated Window instances, failed-hook cleanup and native smoke check with stale anchors/disabled tiles |
| ImGui-Bundle export | Headless import stays lazy, exported module identity and native widget smoke check |
| SDK providers | Shared contract suite for built-in and replacement providers |
| Packaging | Clean environment install and directory/wheel fixture equivalence |

When GUI/native/backend tests cannot run, state the exact unverified behavior. Headless unit tests do not establish native rendering or OS keychain correctness. Test normal and disabled built-in paths. Verify no leaked threads/processes/sockets at cooperative shutdown; document the non-cooperative trusted-thread limit.

## Completing work

Report the concrete behavior changed, relevant verification and remaining material limits. Keep design status honest: documentation is not implemented functionality. Update acceptance evidence when a milestone is actually complete. Leave installation, untrusted-plugin sandboxing and richer expression syntax deferred unless the task explicitly brings them into scope.
